# BrandLab — Project Context

This is the single reference for how BrandLab works: architecture, data flow, the native code on each platform, widgets, build-time generation, platform limits and known behaviours. For setup and commands, see the [README](../README.md).

---

## 1. Purpose

BrandLab is a learning project that shows how **dynamic app branding** works on a real device:

- switching the **launcher icon** at runtime,
- switching the **app display name** (Android only),
- rendering **home screen widgets** (Jetpack Glance on Android, WidgetKit on iOS),
- driving all of this from a simulated **engagement state** (for example, "missed 3 days" changes the app to a "Sad" look).

Every feature calls the real platform API. A native call that fails is reported as a failure, never shown as a success.

## 4. Architecture

```
┌──────────────────────────────────────────────────────────────┐
│ Screens (app/)                                               │
│   read state + call actions from useBranding()               │
└──────────────┬───────────────────────────────────────────────┘
               │
┌──────────────▼───────────────────────────────────────────────┐
│ BrandingContext (src/state)                                  │
│   state · theme colours · capabilities · launcherVariant     │
│   status (last operation, tagged by kind)                    │
└──────────────┬───────────────────────────────────────────────┘
               │
┌──────────────▼───────────────────────────────────────────────┐
│ Services (src/services) — all rules live here                │
│   engagementService  action → new BrandingState (pure)       │
│   brandingService    save state, then icon + widget calls    │
│   storageService     AsyncStorage read/write                 │
│   dynamicIcon / dynamicAppName / widget services             │
└──────────────┬───────────────────────────────────────────────┘
               │  NativeBranding (src/native) — may be null
┌──────────────▼───────────────────────────────────────────────┐
│ Expo Module "BrandingNative" (modules/dynamic-branding)      │
│   Kotlin on Android · Swift on iOS                           │
└──────────────┬───────────────────────────────────────────────┘
               │
   PackageManager / Glance          UIKit / App Group / WidgetKit
```

Rules:

- **Screens contain no branding rules.** They display state and call context actions.
- **Services never throw to the UI for native failures.** Each returns an `OperationResult` `{ ok, message }`.
- **`NativeBranding` can be `null`** (Expo Go, web, Jest). Every service checks for this and returns `ok: false` with a "needs a native build" message.

## 5. State model

### `BrandingState` (canonical, persisted)

Stored as JSON in AsyncStorage under the key **`brandlab.state.v1`**.

| Field | Meaning |
| --- | --- |
| `variant` | `default`, `happy`, `sleepy`, `sad` or `celebration` |
| `engagement` | Last simulated action |
| `lastActivityAt`, `updatedAt` | ISO timestamps |
| `streak`, `dailyProgress` | Activity metrics (`dailyProgress` is 0–1) |
| `appName` | Selected display-name preset |
| `theme` | `system`, `light` or `dark` (in-app theme only) |

`readBrandingState` merges saved JSON over `INITIAL_STATE`, so adding a field with a default is backwards-compatible. Renaming or changing the meaning of a field should bump the storage key.

`BrandingProvider` renders nothing until the saved state has loaded, so the UI never flashes the defaults.

### Other context values

- **`launcherVariant`**: the icon the native side reports as currently active (`getActiveIcon`). It can differ from `state.variant` if a native call failed.
- **`capabilities`**: what the platform supports (from `getCapabilities`, with a JS fallback).
- **`status`**: the last operation result, tagged with an `OperationKind` (`icon`, `name`, `widget`, `scenario`). Screens render `<OperationNotice kinds={[…]} />`, so each result only appears on the screen that caused it.

### Engagement rules (`engagementService.applyEngagementAction`)

| Action | Variant | Effect |
| --- | --- | --- |
| `activeToday` | happy | streak + 1, progress ≥ 72% |
| `missedOneDay` | sleepy | streak 0, progress 0, last activity −1 day |
| `missedThreeDays` | sad | streak 0, progress 0, last activity −3 days |
| `missedSevenDays` | sad | streak 0, progress 0, last activity −7 days |
| `goalCompleted` | celebration | progress 100%, streak ≥ 1 |

The function is pure and takes `now` as a parameter, so it is easy to test.

## 6. Data flow

**Running a scenario or applying an icon:**

1. Screen calls `runEngagement(action)` or `chooseVariant(variant)`.
2. A new `BrandingState` is computed (by `engagementService` for a scenario).
3. `brandingService.commitBrandingState` **saves to AsyncStorage first**, then in parallel:
   - `setIcon(variant)` → native launcher switch
   - `updateWidget(payload)` → native widget write + refresh
4. The context updates `state`, sets `launcherVariant` if the icon call succeeded, and records a `status`.

**Changing the app name** calls `setAppName(name)`. JS state is updated and saved **only if** the native call succeeds.

**Widget payload (`WidgetPayload`)** is a compact projection of the state: `variant`, `stateLabel`, `streak`, `dailyProgress`, `lastActivityAt`, `updatedAt`. Widgets run in a different process and only ever read this payload.

## 7. Native module API

Module name: **`BrandingNative`**. All methods are async.

| Method | Android | iOS |
| --- | --- | --- |
| `getCapabilities()` | All supported | Icons if `supportsAlternateIcons`; widgets if iOS ≥ 17; name = `requires-rebuild` |
| `getActiveIcon()` | Reads native prefs | Reads `alternateIconName` |
| `setIcon(variant)` | Switches activity alias | `setAlternateIconName` (`nil` for default) |
| `setAppName(name)` | Switches activity alias | Always `ok: false` (not supported) |
| `updateWidget(payload)` | Writes SharedPreferences, `updateAll` | Writes App Group defaults, `reloadAllTimelines` |

## 8. Android implementation

### Launcher icon and name: activity aliases

Android can't change an app's icon or label at runtime. Instead, the manifest declares many **`<activity-alias>`** entries that all point to `MainActivity`. Each has its own icon and label, and exactly one is enabled at a time.

- The config plugin removes the `MAIN/LAUNCHER` filter from `MainActivity` and generates **20 aliases** (5 icons × 4 names), named `.BrandLab_<variant>_<nameKey>`. Only `BrandLab_default_default` is enabled at install.
- `setIcon` / `setAppName` combine the requested value with the current other value (read from native prefs `brandlab.native`). They **enable the target alias first**, then disable the other 19, using `DONT_KILL_APP`.
- On success, the chosen `variant` / `appNameKey` is saved to `brandlab.native` prefs. That is what `getActiveIcon` reads.
- Labels and icons must exist at build time. A new name or icon needs a rebuild.

### Glance widget

- `BrandLabGlanceWidget` (`BrandLabWidget.kt`) has two responsive sizes: small (180×110dp) and medium (320×150dp). The medium size adds a large percentage.
- `storeState` writes the payload to SharedPreferences `brandlab.widget` with **`commit()`** (synchronous; it runs on `Dispatchers.IO`), then calls `updateAll`. A background `apply()` could let the widget render stale values.
- `provideGlance` reads the prefs and renders a card with mood, streak, a progress bar and the last-activity date.
- **Light/dark**: colours are `androidx.glance.color.ColorProvider(day, night)` pairs and follow the system dark mode.
- **Tap** opens the app through `getLaunchIntentForPackage`. `MainActivity` itself has no launcher filter, so this resolves to whichever alias is enabled.
- `updatePeriodMillis = 0`: the widget only updates when the app writes new data.

Inspect after prebuild: `android/app/src/main/AndroidManifest.xml` and `android/app/src/main/res/xml/brandlab_widget_info.xml`.

## 9. iOS implementation

### Alternate icons

- The primary icon comes from `app.config.ts` (`icon`). The config plugin copies four more icon sets, `AppIcon-Happy`, `AppIcon-Sleepy`, `AppIcon-Sad` and `AppIcon-Celebration`, into `Images.xcassets`. It also sets `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES`.
- `setIcon` maps `default` to `nil` (primary) and others to `AppIcon-<Capitalized>`. iOS shows its own system alert when the icon changes. Errors from iOS are returned to JS.

### Display name

iOS has **no supported runtime API** to change `CFBundleDisplayName`. `setAppName` always returns `ok: false`, and the App name screen explains this. To change it, edit `app.config.ts` and rebuild.

### WidgetKit extension

- Source: `targets/widget/BrandLabWidget.swift`. Declared by `targets/widget/expo-target.config.js` (iOS 17 minimum, bundle id suffix `.widget`).
- The app and the extension share the App Group **`group.com.brandlab.demo`**. `updateWidget` stores the payload dictionary under `brandlab.widget.payload` and calls `WidgetCenter.shared.reloadAllTimelines()`.
- `BrandLabProvider` reads the payload into a `TimelineEntry` and asks for another read after 2 hours. Supported families: `.systemSmall` and `.systemMedium`.
- **Light/dark**: the container background is a dynamic `UIColor` that matches the app's light and dark surfaces. Text uses `.primary` / `.secondary`.
- **Signing**: set `ios.appleTeamId` in `app.config.ts`. The App Group must be enabled for both targets in your Apple Developer account.

## 10. Build-time generation (Prebuild)

`android/` and `ios/` are generated output and are **not committed** (Continuous Native Generation). After cloning, run `npx expo prebuild`. Everything native that matters lives in:

| Source | Generates |
| --- | --- |
| `app.config.ts` | Bundle IDs, App Group entitlement, plugins list |
| `plugins/with-brandlab-native.js` | 20 Android aliases, `brandlab.xml` label strings, widget receiver + `brandlab_widget_info.xml`, density icon copies, iOS alternate icon sets + build setting |
| `targets/widget/` | WidgetKit extension target (via `@bacons/apple-targets`) |
| `modules/dynamic-branding/` | Autolinked native module (Kotlin + Swift) |

Icons are regenerated with `swift scripts/generate-icons.swift assets/icons` (macOS). It writes the 1024px PNGs and `assets/icons/android/mipmap-*/brandlab_<variant>.png`.

## 11. Values that must stay in sync

These values are hardcoded in several languages. Change all of them together, then run `npx expo prebuild`.

| Value | Locations |
| --- | --- |
| Variants `default, happy, sleepy, sad, celebration` | `src/types/branding.ts`, `src/constants/branding.ts`, plugin `variants`, Kotlin `variants`, Swift `variants`, widget accent colours (Kotlin + Swift), `scripts/generate-icons.swift`, `assets/icons/` |
| Name presets (key ↔ label: `default` BrandLab, `active` BrandLab Active, `focus` BrandLab Focus, `celebration` BrandLab Celebration) | `APP_NAME_OPTIONS` in `src/constants/branding.ts`, plugin `namePresets`, Kotlin `nameKeys` |
| App Group `group.com.brandlab.demo` | `app.config.ts`, `targets/widget/expo-target.config.js`, `BrandingNativeModule.swift`, `targets/widget/BrandLabWidget.swift` |
| Widget payload key `brandlab.widget.payload` | `BrandingNativeModule.swift`, `targets/widget/BrandLabWidget.swift` |
| Variant accent colours | `src/constants/branding.ts`, `BrandLabWidget.kt`, `BrandLabWidget.swift`, `generate-icons.swift` |

### Adding a new icon variant (checklist)

1. Add it to the `BrandingVariant` type and `BRANDING_VARIANTS`.
2. Add it to `variants` in the plugin, Kotlin module and Swift module.
3. Add an icon spec to `generate-icons.swift` and regenerate icons.
4. Add an accent colour to both widgets.
5. Optionally map an engagement action to it.
6. Run `npx expo prebuild`, then rebuild both apps.

## 12. Platform limitations

| Capability | Android | iOS |
| --- | --- | --- |
| Launcher icon | Only predeclared aliases. Launchers may cache the old icon briefly. | Only compiled alternate icon sets. The system shows a confirmation alert. |
| Display name | Only predeclared labels. New labels need a rebuild. | Not supported at runtime. Rebuild needed. |
| Widgets | The launcher decides when to redraw. | WidgetKit reload budgets apply. `reloadAllTimelines` is a request, not a guarantee. |
| Background updates | No unrestricted background refresh. | Extensions are not kept running. |
| Expo Go | Not supported (custom native module + receiver). | Not supported (custom module + extension target). |

A successful result means the platform **accepted** the request. It does not guarantee a third-party launcher has repainted.

## 13. Known behaviours and gotchas

- **The app closes after an icon or name change on some launchers** (seen on Samsung One UI). The alias that launched the running task is disabled. This is expected; reopen the app from the launcher. The App name screen warns about it.
- **Hidden routes in tabs**: `app-name` is hidden with `tabBarButton: () => null`. **Don't use `href: null`**: in this Expo Router version it makes the route unreachable, so links to it silently do nothing.
- **Tab bar height**: don't set a fixed `tabBarStyle.height` or `paddingBottom`. That overrides the safe-area inset, and the bar ends up under Android's navigation buttons.
- **Kotlin `Coroutine` functions**: inside `AsyncFunction("x") Coroutine { … }` the lambda label is `@Coroutine`, not `@AsyncFunction`. Prefer `if/else` over labelled returns.
- **Widget theme** follows the **system** dark mode, not the in-app Appearance setting.

## 14. Testing and verification

Automated tests (`src/services/__tests__`) cover:

- engagement rules (action → variant, progress, timestamps),
- storage round-trip,
- icon service reporting failure when the native module is missing.

Only `**/__tests__/**/*.test.ts` files run.

Manual checks on a device:

1. **Icons tab**: apply a variant. The launcher icon changes and the card shows **ON LAUNCHER**.
2. **App name** (Home → App display name), Android: choose a preset. The launcher label changes, and the app may close.
3. **Widgets**: add the BrandLab widget from the launcher's widget picker, run a scenario, and check that the widget updates. Toggle system dark mode to check the widget theme. Tap the widget to open the app.
4. **Settings**: the capability report matches the platform.

Useful Android commands:

```sh
adb shell dumpsys package com.brandlab.demo | grep -A25 disabledComponents   # which alias is active
adb shell run-as com.brandlab.demo cat shared_prefs/brandlab.native.xml        # native icon/name state
adb shell run-as com.brandlab.demo cat shared_prefs/brandlab.widget.xml        # widget payload
adb shell cmd uimode night yes|no                                              # toggle dark mode
```
